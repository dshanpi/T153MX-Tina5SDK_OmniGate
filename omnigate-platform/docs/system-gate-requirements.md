# OmniGate 系统发布门禁要求

本文定义 OmniGate Industrial Desktop 的统一发布门禁。文中的“必须”“不得”是强制
要求；“建议”不是阻断条件。机器可读策略位于
`omnigate-platform/gates/system-gates.json`。

## 1. 判定模型

每个门禁只能使用以下状态：

- `passed`：本次目标构建和目标硬件的全部必需证据有效，且全部准则满足；
- `passed-with-limitations`：核心准则满足，但存在已明确记录且不被本发布级别禁止的限制；
- `failed`：准则未满足，或证据证明发生失败；
- `not-run`：尚未执行或证据不足；
- `not-applicable`：经评审确认对目标 profile/声明不适用，并记录理由。

`not-run`、`not-applicable` 和“设备已枚举”不得改写成 `passed`。一个门禁失败时，整体
结论必须失败；证据缺失时不得根据历史经验补判。`passed-with-limitations` 只有机器策略
明确允许时才可放行。

发布级别：

| 级别 | 强制门禁 | 允许限制 |
| --- | --- | --- |
| development | G0–G3 | 仅 G3，可明确列出未接外设、人工测试或开发安全限制 |
| release-candidate | G0–G4 | 不允许 |
| production | G0–G6 | 不允许 |

Enhanced profile 额外强制 G7。只要发布材料声称 CANopen、Modbus 或 EtherCAT 互操作，
G5 就是强制项，不受发布级别影响。

## 2. 证据通则

每份证据必须能关联到目标源码、镜像、板卡和执行时间。镜像证据至少记录文件名、字节
数、SHA-256、分区表、板卡描述 ID、构建配置和工具版本。板端证据必须记录硬件型号、
启动版本以及实际传输通道。

以下情况使下游证据失效，必须重跑相关门禁：

- 源码、配置、工具链、板级 DTS、rootfs 或固件内容发生变化；
- 被测镜像 SHA-256 改变；
- 换用不同板型、关键外设或不同硬件版本；
- 测试过程中修改系统配置但未恢复并重新采证。

日志摘要不能替代原始记录。人工确认必须包含执行人/来源、时间、动作和结果。敏感数据
应脱敏，但不得删除影响判定的错误、退出码或时间线。

## 3. 各门禁要求

### G0：源码与契约完整性

必须通过主机测试、Python/Shell/JavaScript 静态检查、JSON/Schema 检查、平台组件与
profile 引用检查，并证明 overlay 与目标 SDK 一致。测试跳过、依赖缺失或清单漂移均
阻断通过。

### G1：可追溯镜像

必须从已声明配置完成干净或定向清理后的构建，禁止复用会隐藏源码变化的 Buildroot
旧 stamp。必须记录镜像身份、12 分区布局（另含 Boot0/Boot1）和发布包校验和。只生成
文件但没有构建成功记录，不能通过。

### G2：部署与冷启动

传输到烧写端的 SHA-256 必须与本地一致，写入后必须回读校验成功，Linux 必须在 120 秒
内达到可用状态。报告必须区分 `full_erase` 与 `partition`；此前任务创建过分区布局，
不等于当前 `partition` 任务完成了全擦写。USB 中断、校验未完成或任务状态不明均失败，
不得用“多数分区已写入”放行。

### G3：Lite 功能与安全行为

必须覆盖登录失败、登录、角色权限、CSRF、设备/点位 CRUD、版本与审计、SQLite 完整性、
服务状态和有界自愈。必须检查真实 framebuffer、触摸输入证据、分区、接口、关键驱动及
启动日志，且不得出现 panic、Oops 或 OOM。

没有外部从站时，只能验证组件存在、接口枚举和空载安全行为。不得发送 CANopen、Modbus
或 EtherCAT 控制帧，不得声明协议互操作通过。触摸驱动注册和 `/dev/input/event*` 只
证明枚举；物理触摸通过还需要真实操作或可审计的输入事件。

### G4：长期稳定性

必须连续运行至少 24 小时，按不大于 60 秒间隔保留时间戳样本；计划重启窗口要单独标记。
Web/HMI 健康率必须不低于 99.5%，不得出现非计划重启或内核异常。稳定段首尾 RSS 增长
不得超过 20%，日志和数据库增长分别不得超过 50 MiB。必须完成一次受控 Web 故障注入，
确认 supervisor 恢复且没有重启风暴。

### G5：现场总线互操作

每项声明必须连接命名的真实从站/测试夹具，保存配置、协议报文或工具输出，并覆盖声明的
读写路径、超时与恢复。任何可能驱动真实设备的写操作必须事先获得明确授权并限定地址、
值和停止条件。枚举、进程启动或链路 Up 均不能替代互操作证据。

### G6：生产安全与更新

生产放行必须证明唯一设备身份、首次强制改密、调试入口关闭、默认拒绝防火墙、安全启动、
签名 OTA、失败自动回滚和产品威胁模型。开发板上的 HTTPS、自签名证书或单次 A/B 分区
写入不能替代这些要求，也不得表述为 IEC 62443 认证。

### G7：Enhanced 运行时隔离

每个声称支持 Enhanced 的板型都必须在实板验证 OCI CPU/内存/PID 限制、丢弃 capabilities、
不映射硬件设备、Node-RED 流程与凭据持久化、掉电恢复和负载稳定性。主机临时容器测试
只能作为 G0 证据，不能使 G7 通过。

## 4. 执行与审查

使用 `make gate RELEASE_CLASS=development PROFILE=lite` 检查当前状态与策略是否一致。
候选版或生产版分别使用 `RELEASE_CLASS=release-candidate`、`production`；Enhanced 使用
`PROFILE=enhanced`，声明现场总线互操作时增加 `GATE_ARGS=--claim-fieldbus`。

工具只校验状态闭包，不替代证据审查。评审者必须逐项打开 `release-status.json` 中列出的
证据，确认内容属于同一目标构建。任何豁免必须包含负责人、原因、影响、到期时间和补救
计划；豁免不会把失败或未执行改成通过。
